Maintenance service

isledb maintenance is a service that looks after one IsleDB database: it compacts the files the writer saves, keeps the database's metadata short so readers load it quickly, and deletes what is no longer needed. It serves no API; it has only an admin address for health checks and metrics.

Run it in production. Without it, every save adds a file that readers check and that is never deleted, so reads slow down and storage grows.

Start maintenance

With a configuration file:

isledb maintenance --config /etc/isledb/isledb.yaml

Or with flags:

isledb maintenance \
  --bucket-url 's3://my-bucket?region=us-east-1' \
  --prefix prod/accounts

Maintenance reads storage credentials from the usual places for your cloud provider, like the writer. It needs to read, write and delete objects under the database's prefix. Credentials never go in its configuration.

Maintenance and the writer can start in any order. Maintenance prepares its work, and the writer publishes it with its next save, so its results reach readers only while a writer is running.

Run one maintenance per database

Only one maintenance process works on a database at a time. If you start a second one for the same database, it takes over, and the first one stops working and reports not ready.

  • Run exactly one replica.
  • When you deploy a new version, stop the old one before starting the new one. In Kubernetes, use strategy: Recreate. A short overlap does no harm: the newer one takes over.

A replaced process stays running, not ready, and doesn't take the database back on its own. Stop whichever one shouldn't be running.

Configuration

You can set each option in a YAML file, as an environment variable, or as a flag. Flags take priority over environment variables, which take priority over the file.

A typical configuration:

bucket_url: s3://my-bucket?region=us-east-1
log_level: info

maintenance:
  prefix: prod/accounts
  scratch_dir: /var/lib/isledb/scratch

Every option of the maintenance section, at its default where it has one:

maintenance:
  admin_listen: 127.0.0.1:8061
  shutdown_drain: 0s

  prefix: prod/accounts          # required
  scratch_dir: ""                # empty: the user's cache directory

  change_feed:
    retain_for: 0s               # 0s keeps all history; e.g. 168h

To check a configuration without starting maintenance:

isledb maintenance --config isledb.yaml --check

Options

File Flag Environment Default Meaning
maintenance.prefix --prefix ISLEDB_MAINTENANCE_PREFIX The database to maintain; / for the bucket root. Required.
maintenance.scratch_dir --scratch-dir ISLEDB_MAINTENANCE_SCRATCH_DIR the user's cache directory Where compaction keeps the files it is merging.
maintenance.change_feed.retain_for --change-feed-retain-for ISLEDB_MAINTENANCE_CHANGE_FEED_RETAIN_FOR 0s How long the database's change-feed history is kept; 0s keeps it all.
maintenance.admin_listen --admin-listen ISLEDB_MAINTENANCE_ADMIN_LISTEN 127.0.0.1:8061 Health checks and metrics.
maintenance.shutdown_drain --shutdown-drain ISLEDB_MAINTENANCE_SHUTDOWN_DRAIN 0s How long to report not ready before stopping.

Maintenance has no API, so listen, auth and tls don't apply: setting them is an error.

Scratch space

Compaction writes the files it is merging to scratch_dir instead of holding them in memory. Give it a local disk with room for the files of the compaction in progress, and in a container mount a volume there: the default cache directory may be small or read-only. Maintenance removes its own files when it stops, and on its next start it removes any a crash left behind. It never deletes anything else in the directory.

Change-feed history

By default the change feed keeps every change forever. With change_feed.retain_for set, maintenance deletes changes older than that. A consumer whose saved position is older than what is kept can't resume from it without a gap: it either accepts the gap and continues from the oldest change kept, or rebuilds its state from a snapshot of the database. Set it longer than the longest time a consumer may be stopped.

Health checks

Served on admin_listen, without authentication.

Path Answers
/healthz 200 while the process is running.
/readyz 200 while maintenance is working. 503 after another maintenance process has taken over, and while shutting down.
/metrics Prometheus metrics.
/debug/pprof/ Go profiling.

Metrics

Metric Shows
isledb_maintenance_running 1 while maintenance works on the database; 0 after another maintenance process took it over.
isledb_maintenance_cycles_total, isledb_maintenance_cycle_errors_total Rounds of work, and rounds that failed and are retried.
isledb_maintenance_last_cycle_timestamp_seconds When the last round completed.
isledb_maintenance_waiting_for_writer 1 while finished work waits for the writer to publish it.
isledb_maintenance_compaction_jobs_total Compactions, counted when they run, including any the writer then rejects.
isledb_maintenance_compaction_l0_merges_total, isledb_maintenance_compaction_moves_total Of those, merges of newly saved files with each other, and moves of files to another level without rewriting them.
isledb_maintenance_compaction_read_bytes_total, isledb_maintenance_compaction_rewritten_bytes_total Bytes compaction read from and wrote to storage: most of maintenance's storage cost.
isledb_maintenance_compaction_moved_bytes_total Bytes moved without being rewritten.
isledb_maintenance_compaction_oversized_jobs_total Compactions larger than usual, run because the level they write into could not be made smaller first. Each writes one unusually large file.
isledb_maintenance_commands_rejected_total Finished work the writer refused to publish. The writer logs why.
isledb_maintenance_compaction_rejected_bytes_total Bytes compaction wrote for work the writer refused. The files are deleted later.
isledb_maintenance_checkpoints_total Checkpoints of the database's metadata prepared for the writer to publish.
isledb_maintenance_deleted_objects_total{kind}, isledb_maintenance_delete_failures_total{kind} Objects deleted from storage, and deletes that failed and are retried, by kind: sst, change_batch, snapshot, page.

What to alert on:

  • Stuck: time() - isledb_maintenance_last_cycle_timestamp_seconds above a few minutes, or cycle_errors_total rising. Usually a storage permission problem, or no space in scratch_dir; the log says which.
  • No writer: waiting_for_writer at 1 for minutes. Maintenance's work is ready but no writer is publishing it, so files pile up.
  • Refused work: commands_rejected_total rising steadily. An occasional refusal is normal: the writer refuses work on files that changed while it was being done, and maintenance redoes it. A steady rise means work is being thrown away; the writer's log says why.
  • Replaced: isledb_maintenance_running at 0: another maintenance process took over, and this one does no more work. See Run one maintenance per database.

Shutting down

When maintenance receives SIGTERM or SIGINT, it stops the round in progress, removes its scratch files and exits, within about 30 seconds. A round stopped partway is safe: its work is redone after the next start.
